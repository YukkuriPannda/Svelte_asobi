# サブエージェントの運用

このプロジェクトでは親Agent（Sol）が要求整理、担当の割り当て、共有契約の管理、コードレビュー、統合判断を担当する。実装担当はコード変更と必要な検証を行う。ユーザーがモデル・effort・作業範囲を指定した場合は、その指定を優先する。

## 役割とモデル

| 担当 | モデル・effort | 用途 |
| --- | --- | --- |
| 親Agent | Sol（現在のセッション設定） | 要求整理、分担、差分レビュー、担当の検証結果の確認、統合判断 |
| 小規模の実装・テスト担当 | Devin CLIの `swe-2-high` | 仕様と編集箇所が確定した変更、限定した回帰テスト、独立した再現確認 |
| 中規模の実装担当 | Codexの `gpt-6-luna` / `max` | 変更箇所の探索や複数モジュールの調整が必要な実装 |
| 大規模・高リスクの実装／レビュー担当 | Claude Codeの `opus` / `high` | 曖昧な仕様、難しい統合、認証・データ整合性などの境界に関わる実装と独立レビュー |

Lunaの標準は `max` とするが、ユーザーが `high` を指定した依頼では `gpt-6-luna` / `high` を使用する。モデルを変更するときは変更先と理由を明示し、ユーザーが指定した経路を別のサービスへ置き換えない。

SWE-2はインストール済みDevin CLIから、正確なモデルID `swe-2-high` を指定する。Opusは `claude-code-delegate` スキルに従い、Claude Codeで `--model opus --effort high` を指定する。完了したJSONの `modelUsage` に `claude-opus-5-5` が含まれることを確認する。指定したモデルを利用できない場合は、その事実を報告する。

## 委任を開始する前

親Agentは作業の規模、曖昧さ、リスクを整理し、実装担当とレビュー体制を決める。独立して実装できる作業だけを分割し、同時に動かす実装担当は最大3名とする。依存する作業は順番に進める。短い文書の編集など、分担の調整にかかる手間が作業量を上回る場合は親Agentが直接担当する。

担当を起動する前に、ユーザーへ次の内容を提示する。

- 正確なモデル名とreasoning effort。設定できない場合はその旨。
- その組み合わせを選ぶ理由と、実装・テスト・レビューの担当区分。
- 編集してよいファイル・モジュールと、編集してはいけない範囲。
- 外部CLIを使う場合は、その呼び出しで外部サービスへ渡すファイル・差分・ログの範囲。

共有する型、スキーマ、公開シグネチャ、設定キー、移行契約は委任前に固定する。変更が必要になった場合は、関係する担当を止めて親Agentが契約を修正し、再配布する。

## 実装担当への依頼

各依頼には以下を含める。

1. 目的、期待する動作、受け入れ条件と必要な証拠。
2. 所有するファイル・モジュール、禁止する編集範囲。
3. 固定した共有契約と、他の担当への依存関係。
4. 必要な検証コマンド、スクリーンショット、手動確認、差分の条件。
5. 既知の問題、作業を止めて親Agentへ相談する条件、完了報告の形式。

担当は共有作業ツリーで作業していることを前提に、他者の変更を戻さない。追加のファイルが必要になった場合は、親Agentが編集範囲を拡張してから変更する。未追跡ファイルや生成処理により、依頼外の変更を巻き込まない。

## 検証の担当

2026-10-03のユーザー指示により、**親Agentは担当のテスト・型チェック・ビルド・Visual比較を再実行しない**。実装担当が必要な検証を実行し、親Agentは差分と報告された証拠を確認する。上位の運用指針にある親Agentによる独立再実行より、このプロジェクトでのユーザー指示を優先する。

必要なコマンドとVisual比較の手順は [AGENTS.md](../AGENTS.md#検証) と [.visual/README.md](../.visual/README.md) に従う。再検証を省くことは、実装担当の検証やコードレビューを省くことではない。

独立したテストが追加の証拠になる場合は、別の担当へ依頼する。期待値は要求・再現手順から決め、実装コードの挙動をそのまま期待値にしない。修正後の検証も担当が行う。

担当の検証報告には次を記載する。

- 変更したファイルと、実行した正確なコマンド。
- 成否、件数、失敗の理由、今回追加したエラーと既存エラーの区別。
- Visual差分の確認対象、baselineを更新した理由と対象。
- 実行環境、スクリーンショットなどの証拠、未確認事項。

エミュレーターや同じブラウザープロファイルは一人の担当だけが操作する。ローカル、エミュレーター、物理端末、iPad、クラウドの結果を分けて報告する。

## コードレビュー

コードレビューとテスト結果の確認は別の作業として扱う。テスト成功だけでコードレビュー済みとしない。実装担当は自分の変更を最終承認できない。

| 変更の規模・リスク | レビュー体制 |
| --- | --- |
| 小規模・低リスク | 親Agentの差分レビューで受け入れ可能 |
| 中規模 | 親Agentがレビューし、追加の証拠になる場合は別担当のテストまたはレビューを割り当てる |
| 高リスク、境界をまたぐ変更、大規模または戻しにくい変更 | 独立した第二レビューを必須とする。原則としてOpus 5.5 / highを使用する |

認証、セキュリティ、データ整合性、並行処理、公開API、移行に関わる変更は、独立した第二レビューの対象とする。Opus自身が実装した場合は別モデルがレビューする。外部CLIのレビュー担当には読み取り専用の権限を与える。

親Agentは編集境界、要求との一致、固定した契約、関連ページへの影響、失敗時の動作、検証の不足を差分から確認する。レビュー結果は指摘内容・対応状況・残る不確実性を報告する。受け入れ判断のために実行証拠が足りない場合は担当へ追加確認を依頼する。

## レビュー用の開発サーバー

UI変更の完了報告には、起動している開発サーバーの具体的なURLを付ける。対象ページへ直接移動できるURLを提示し、localhostと他端末からアクセスできるURLを区別する。停止しているサーバーを利用可能と報告しない。

サーバー起動と起動状態の確認は、親Agentも行ってよい。これは担当のテストを再実行することには当たらない。未追跡のコンテンツを生成物へ巻き込むおそれがある場合は、データ生成を含まない `npm run dev:svelte` を使用する。

## 外部CLIへ渡す情報

ユーザーは、現在の依頼と担当範囲に必要な最小限の非公開リポジトリ内容・差分・ログを、Devin CLI経由でCognition、Claude Code経由でAnthropicへ送ることを許可している。呼び出しごとに送信範囲を明示する。この範囲内で許可を取り直さない。

秘密情報、認証情報、個人データ、依頼外・担当範囲外のファイルを送る場合、別のサービスを使う場合、追加の永続化を有効にする場合は、新しい明示的な許可を必要とする。CLIを起動できたことと、指定モデルが作業を完了したことを区別する。実行中のCLIを待たずに同じ依頼を重複起動しない。

ローカルQwenは、ユーザーが求めた場合や、機械的に確認できる限定した列挙に使用する。コードレビューの承認者や主要な実装担当にはしない。ブリッジ経由の情報が必ず端末内に留まるとは扱わない。

## 失敗した場合

再割り当ての前に原因を分類する。

- 仕様の誤解: 依頼文・契約を修正してから再試行する。
- 探索不足: Luna maxまたはOpus 5.5 Highへ引き上げる。
- 大きすぎる、結合が強すぎる: 作業を分割して順番に進める。
- 契約逸脱、過剰な変更: 親Agentが担当変更だけを安全に戻し、範囲を狭める。他者の変更を巻き込まない。
- 同じ能力不足の繰り返し: より適した担当へ一度引き上げ、同じ原因が二度続いたら親Agentが方針を見直して引き取る。

同じ条件の失敗を、モデル名だけ変えて繰り返さない。ユーザー指定のモデルや経路を変更する必要がある場合は、変更理由を示して相談する。

## 完了とGit操作

完了報告には変更内容、担当モデル・effort、レビュー結果、担当の検証結果、開発サーバーURL、未確認事項、今回の範囲のコミットメッセージ案を記載する。文書だけの変更では、開発サーバーの起動やアプリのテストは不要。

Git操作は [git_rule.md](git_rule.md) に従う。ユーザーが自分でレビュー・mainへのマージ・pushを行うと指定している間は、その操作と本番公開をユーザーに任せる。Cloudflareの操作権限を得たことだけを、デプロイの指示と扱わない。コミットも明示的な依頼を受けてから行う。
