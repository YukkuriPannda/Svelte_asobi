# Git運用ルール

## Git-flow

このリポジトリではGit-flowを採用する。既存の `dev` を一般的なGit-flowの `develop` に相当する開発統合ブランチとして使う。

| ブランチ            | 用途                                     | 分岐元 | 統合先                        |
| ------------------- | ---------------------------------------- | ------ | ----------------------------- |
| `main`              | 公開・リリース済みの安定版               | —      | —                             |
| `dev`               | 次のリリースに向けた開発統合             | `main` | `release/*` を経由して `main` |
| `feature/<slug>`    | 機能、通常の不具合修正、ドキュメント変更 | `dev`  | `dev`                         |
| `release/<version>` | リリース準備・検証・必要な修正           | `dev`  | `main` と `dev`               |
| `hotfix/<slug>`     | 公開版の緊急修正                         | `main` | `main` と `dev`               |

Codexが作る作業ブランチは `codex/feature/<slug>`、`codex/release/<version>`、`codex/hotfix/<slug>` とする。ユーザーがブランチ名を指定した場合はその名前を優先する。slugは内容が分かる英小文字とハイフンを使う。

## 通常の作業

1. 作業前にstatus、現在のブランチ、分岐元を確認する。既存変更をstash・削除・上書きする前に扱いを確認する。
2. 新規の作業は `dev` からfeatureブランチを作る。明示された既存ブランチの継続作業はそのブランチで行う。
3. 一つの目的ごとに小さく変更し、対象の検証とコンポーネント作業記録の更新を行う。
4. `git diff` と `git diff --check` で変更範囲を確認し、今回のファイルだけをstageする。
5. コミットが依頼されたら検証済みの変更をコミットする。push・PR・mergeは依頼された範囲で実行する。
6. featureはレビュー後に `dev` へ統合する。ブランチ境界を残すため、統合時はmerge commit（`--no-ff`）を基本とする。

現在ある `blog-dev`、`works-dev`、`feat-(doc)doc-refactor` などの既存ブランチは、このルールの導入だけでは改名・削除・統合しない。以後の新規作業に命名規則を適用する。

## リリース・緊急修正

- releaseは `dev` から作り、機能追加を止めてリリース準備に集中する。検証後に `main` と `dev` の両方へ統合し、承認されたバージョンを `v<version>` でタグ付けする。
- hotfixは `main` から作り、公開版の問題に絞って修正する。検証後に `main` と `dev` の両方へ統合する。進行中のreleaseがある場合は、そこにも修正を取り込む。
- push・merge・タグ・公開は対象を明示したユーザーの承認を得る。force push、reset、ブランチ削除など履歴や作業を失う操作も明示的な承認が必要。
- 秘密情報、`.env`、認証情報、個人データをコミットしない。
- Visual baseline・manifest・外部画像fixtureは追跡する。`.visual/results/` と `.visual/report/` は生成物として除外する。

## コミット命名規則

Conventional Commits形式を使い、説明は日本語で書く。

```text
<type>(<scope>): <変更内容>
```

scopeは省略可能。コンポーネント名・機能名・ページ名を使う（`header`、`blog-panel`、`home`、`blog`、`photo`、`works`、`visual`、`docs` など）。

| type       | 用途                                  |
| ---------- | ------------------------------------- |
| `feat`     | 機能追加                              |
| `fix`      | 不具合修正                            |
| `docs`     | ドキュメント変更                      |
| `style`    | 整形・空白など動作に影響しない変更    |
| `refactor` | 外部動作を変えない構造変更            |
| `test`     | テスト・Visual Regressionの追加や修正 |
| `build`    | 依存関係・ビルド設定                  |
| `ci`       | CI設定                                |
| `chore`    | その他の保守作業                      |
| `perf`     | 性能改善                              |
| `revert`   | 変更の取り消し                        |

見た目・挙動を変えるUI変更には目的に応じて `feat` または `fix` を使い、整形用の `style` と区別する。

```text
feat(photo): 写真詳細に撮影機材の表示を追加
fix(blog): 記事一覧のサムネイル表示を修正
test(visual): Desktopの基準スクリーンショットを更新
docs: Git-flowとコンポーネント作業記録の運用を追加
```

破壊的変更は `feat(scope)!: 説明` のように `!` を付け、本文に `BREAKING CHANGE: ...` と移行方法を書く。必要なら本文に変更理由・検証・未確認事項を記載する。一つのコミットに無関係な変更を混ぜない。

## タスク完了時のコミットメッセージ提案

ファイル変更を伴うタスクの完了報告には、上記の命名規則に沿った日本語のコミットメッセージ案を必ず含める。今回の変更だけを説明し、無関係な既存変更を含めない。独立した目的が複数ある場合は、目的ごとにコミットを分けた案を示す。

変更がない調査・回答のみのタスクでは提案不要。すでにコミット済みなら、案の代わりに実際のコミットメッセージを報告する。提案はコミット実行の承認を意味しない。
